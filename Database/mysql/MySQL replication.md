MySQL has native built-in replication support. You do not need Redis, Kafka, or another external system to implement the basic leader. 

```txt
	 MySQL Source
┌───────────────┐
│   Database    │
│               │
│ Binary Log    │
└───────┬───────┘
				│
replication connection
				│
				▼
┌───────────────┐
│ MySQL Replica │
│               │
│ Relay Log     │
│      ↓        │
│    Apply      │
└───────────────┘
```
The source writes database changes to its **binary log**. The replica connets to the source, reads those binary-log events, stores them in its **relay log,** and then applies them to its own database.

Binary log: durable stream of changes generated by the source.
Replication receiver: connects to the source and receives binary-log events.
Relay log: Local copy of received events on the replica.
Replication applier: applies those events to the replica's database.
Replication metadata: tracks where the replica is in the source's log.

> MySQL also supports different replication, configurations, including **asynchronous replication, semisynchronous replication, GTID-based replication multi-source replication.**


- create a consistent, read-only point-in-time state for operations such as taking a database backup.
`FLUSH` "Take anythingn MySQL is currently keeping in memory/buffers/state and synchronize or apply it to its place where MySQL is supposed to put the data/state after flusing."

> FLUSH tells MySQL to finish/synchronize certain in-memory or internal state associated with the thing being flushed.

If your goal is replicating leader while leader continue accepting writes while you initialize the follower, then acquiring a global read lock is usually undesirable.

**The problem is that the follower needs an initial snapshot of the leader that corresponds to know replication position.**
