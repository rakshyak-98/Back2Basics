**backend membership and health** A backned can have a reachable network interface while its application process is dead, overloaded, unable to reach its database, or otherwise incapable of successfully completing requests. Health checking therefore determines whether an instance participates in the load-balancing pool. The mechanism below is network and application communication: the balancer periodically sends probes or observes actual traffic outcomes and uses the resulting signals to mark instances healthy or unhealthy.

The exact health-check semantics matter architecturally. A TCP check establishes that the endpoint can accept a TCP connection, but it does not establish that the application is functioning correctly. An HTTP health check can verify that an HTTP endpoint responds successfully, potentially making the check much closer to application readiness. But making health checks too deep creates another dependency problem: If the health endpoint requires every downstream dependency to be healthy, a temporary database or third-party dependency failure can cause every application instance to be removed from service simultaneously. The health signal therefore has to represent the condition that the load balancer actually needs to know **Should I send normal production traffic to this instance?**

At this point the load balancer has two pieces of state: the traffic distribution policy and the current eligible backend set. The next abstraction is **connectio handling.**
