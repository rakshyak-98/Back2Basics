The mechanism is more involved because the balancer terminates or understands the client-side HTTP connection. It can inspect the HTTP request before deciding where to send it. The balancer may maintain a client-facing TCP/TLS connection while establishing a separate backend connection. This separation is what enables capabilities such as path-based routing, host-based routing, header-base routing, HTTP redirects, authentication integration, request rewriting, and TLS termination.

> TLS termination is consequently not a separate reason for having a load balancer; it is a capability that becomes possible when the load balancer operates at a layer where it can terminate TLS and understand the resulting HTTP traffic. The client establishes TLS with the load balancer, the load balancer decrypts the request, makes its routing decision, and can establish another connection to the backend. The backend connection may itself use TLS, producing end-to-end encryption with TLS on both segments, or it may use plan HTTP inside a trusted private network. The choice changes the security boundary and operational cost rather than changing the fundamental load-balancing mechanism.
