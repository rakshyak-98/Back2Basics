# x11

> Legacy network-transparent display protocol — still common via Xorg or XWayland on Wayland sessions.





## Interview Relevance
Classic graphics stack: X server vs clients vs WM, `DISPLAY`/`XAUTHORITY`, and how XWayland changes behavior under Wayland.

## Sources
- [X.Org Wiki](https://wiki.x.org/) — deep-dive
- `man 7 X`, `man 1 xrandr` — deep-dive

## Core Definition
X11 separates the X server (owns GPU/input) from X clients (applications). The window manager decorates and focuses windows. Remote GUIs historically used `ssh -X` forwarding `DISPLAY`.

## Key Concepts
- **Server / client / WM:** WM is a privileged client.
- **`DISPLAY` / `XAUTHORITY`:** which server and which cookie.
- **XWayland:** X apps on Wayland desktops.
- **Network transparency:** powerful historically; weak isolation.

## Technical Details
```bash
echo $DISPLAY
echo $XAUTHORITY
xset q
xrandr --query
xrandr --output HDMI-1 --mode 1920x1080 --rate 60
xinput list
xprop WM_CLASS
```

| Symptom | Check |
|---------|-------|
| Can’t open display | `DISPLAY` set? `xhost` / `xauth` for remote |
| Wrong monitor layout | [[xrandr]]; persist in `~/.xprofile` or DE settings |
| High DPI blur | `Xft.dpi`, `GDK_SCALE` |
| App only fails on Wayland | Force `GDK_BACKEND=x11` to test XWayland |

## Real-World Applications
Fix multi-monitor docking with `xrandr`, and identify window classes with `xprop WM_CLASS` for i3/Sway rules.

## Pros/Cons or Trade-offs
- **Pro:** Decades of tooling and remote-forwarding habits.
- **Con:** Weaker client isolation; every client can historically snoop more of the server.

## Comparison
- vs [[wayland]]: unified compositor model vs separate X server.
- vs [[window manager/X window system (X11)]]: protocol-deep sibling; this note is the ops surface.

## Mistakes to Avoid
- Running `xhost +` on shared machines.
- Assuming XWayland equals full native Xorg behavior for grabs/capture.
- Ignoring `XAUTHORITY` when `DISPLAY` is set but apps still fail.
